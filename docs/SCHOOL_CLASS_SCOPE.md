# Школьные и личные классы

Реализация рассчитана на одну школу SlovaSofi. Для нескольких независимых школ потребуется отдельная сущность school и членство сотрудников, а не повторное использование роли director.

| Роль | Классы | Изменения |
| --- | --- | --- |
| admin | Все школьные и личные | Полный доступ |
| director | Только class_scope = school | Только просмотр |
| teacher | Только собственные школьные и личные | Управление собственными классами |
| student | Назначенные классы | Прежний доступ через student-lessons |

Новые классы создаются школьными по умолчанию. Учитель может выбрать «Личный класс» при создании. Тип и владельца существующего класса меняет только администратор: это предотвращает скрытие школьного класса от директора учителем. Принадлежность показывается на карточках классов.

Общая библиотека уроков доступна директору для просмотра. Назначения, ученики, ответы, прогресс, расписание и приватные аудиозаписи ограничены школьными классами. Изменять назначения, уроки, прогресс, расписание, приглашать учеников или управлять сотрудниками директор не может. Запрет действует через RLS, права RPC и серверные функции, независимо от интерфейса. Старая запись директора в teacher_lesson_editors не даёт права редактирования.

## Применение

Рабочая база не обновляется автоматически от изменения файлов сайта.

1. Сделать резервную копию базы и проверить миграции на тестовом проекте.
2. Применить `supabase/migrations/20261116_school_class_scope.sql` после всех предыдущих миграций. Транзакция сохраняет существующие классы как личные: не раскрывает старых учеников автоматически и не удаляет классы, назначения или прогресс.
3. Обновить Edge Function: `supabase functions deploy manage-teachers` в проекте с корректной Supabase CLI-привязкой.
4. Опубликовать изменённые JS-файлы сайта. Обновление фронтенда требует новой колонки class_scope; сначала применить SQL.
5. Администратору в разделе сотрудников изменить роль нужного аккаунта на «Директор». Для нового сотрудника можно выбрать эту роль при приглашении. Для снятия доступа директора изменить роль на «Учитель»; кнопка удаления старого права редактора для директора не показывается.
6. Под администратором открыть редактор каждого школьного класса, выбрать «Класс школы» и сохранить. Личные классы не переносить. Директору выйти и войти заново.

Директор не должен иметь права владельца проекта Supabase, service_role или административного доступа к базе: такие права обходят RLS. Роль сайта director и доступ к Supabase Dashboard — разные права.

## Проверки

JavaScript: `node --test assets/js/class-scope.test.js assets/js/teacher-data.test.js assets/js/teacher-data-reset.test.js assets/js/security.test.js assets/js/teacher-workspace.test.js`.

Полная проверка SQL выполняется в изолированном PostgreSQL PGlite, без подключения к Supabase и без секретных ключей:

```sh
npm install --prefix /tmp/slovasofi-rls-check --ignore-scripts --no-audit --no-fund @electric-sql/pglite@0.5.16
NODE_PATH=/tmp/slovasofi-rls-check/node_modules node tools/verify-school-scope.cjs
```

Проверка применяет реальные предыдущие миграции, имитируя системные схемы Auth и Storage. Проверяет существующие классы, SELECT/DELETE по всем таблицам, записи аудио, запрет INSERT/UPDATE директором, старые членства и права редактора, запрет самоповышения роли, учителей, ученика, административный перенос класса. Это проверка PostgreSQL RLS; развёрнутые Edge Functions, реальный Storage и браузер после публикации нужно проверить отдельно.

Ручная приёмка: создать одним учителем школьный и личный класс; проверить видимость под учителем, директором и администратором. Под директором проверить прямой запрос личного class_id, отсутствие кнопок изменения, просмотр школьного прогресса и расписания. Под учеником проверить прежние уроки и ответы.
