# Резервные копии: вручную или по расписанию

## Ручная копия через браузер — без установки программ

Этот вариант не требует Docker на вашем компьютере, API-ключей R2 или расписания. Вы вручную запускаете GitHub Actions, скачиваете готовый зашифрованный файл и загружаете его через сайт Cloudflare.

1. В закрытом репозитории `alm1e/SlovaSofi-backups` должны быть три Repository secrets: `SUPABASE_DB_URL` (Session pooler с паролем базы, порт 5432), `SUPABASE_SERVICE_ROLE_KEY` (legacy серверный ключ) и `RESTIC_PASSWORD` (не менее 32 символов). Сохраните пароль шифрования отдельно в менеджере паролей. Если эти секреты уже настроены, повторно вводить их не нужно. R2-секреты этот workflow не использует.
2. Откройте **Actions → SlovaSofi manual download → Run workflow → main → Run workflow**. `initialize` здесь нет. На время копирования не загружайте и не удаляйте файлы школы.
3. Дождитесь зелёного результата. Внизу страницы запуска, в **Artifacts**, нажмите **SlovaSofi-manual-backup**. Скачайте его сразу: срок хранения в GitHub — **1 день**. Архив содержит зашифрованную копию базы, файлов Storage и кода `main`; программа проверяет извлечение и SHA-256 до предложения скачивания.
4. Распакуйте скачанный ZIP. Внутри будут **`.restic.tar`** и **`.sha256`**. Только зашифрованный архив и его контрольная сумма публикуются как artifact; открытые SQL, записи учеников, ключи и пароль туда не входят.
5. Откройте **Cloudflare → R2 → slovasofi-backups → Upload** и загрузите эти два файла. Bucket оставьте закрытым. Затем скачайте `.restic.tar` обратно и проверьте его SHA-256 командой `Get-FileHash -Algorithm SHA256 ПУТЬ_К_ФАЙЛУ` — он должен совпадать с `.sha256` и Summary запуска. До этого сохранность облачной загрузки не подтверждена.

Каждую следующую копию запускайте той же кнопкой; автоматически ничего не включается. Каждая копия — отдельный независимый архив, старые версии не удаляются. Пароль `RESTIC_PASSWORD` нужен для восстановления: смена секрета в GitHub не меняет пароль старых архивов. При распаковке `.restic.tar` появляется папка `encrypted-repository`; порядок восстановления и ограничения состава копии описаны ниже и в [полной инструкции](BACKUPS.md).

## Ручная копия без API-ключей Cloudflare

Этот вариант не использует GitHub Actions или R2 API. Вы вручную запускаете создание копии и загружаете **один зашифрованный архив** в закрытый bucket через Cloudflare Dashboard.

1. Установите и запустите **Docker Desktop** (нужен для `supabase db dump`). Также нужны Node.js, Supabase CLI, Git, tar и restic. На этом компьютере restic уже находится в `artifacts/private-backups/backup-tools`; скрипт найдёт его автоматически.
2. Сохраните в менеджере паролей URL **Supabase → Connect → Session pooler**, порт **5432**, с паролем базы; серверный legacy `service_role` из API keys; отдельный пароль шифрования длиной не менее **32 символов**. Спецсимволы пароля базы в URL должны быть URL-encoded. Эти значения не отправляйте в чат. Потеря пароля шифрования означает потерю доступа к копии.
3. Из корня проекта запустите:

   ```powershell
   powershell -NoProfile -File .\tools\backups\manual-backup.ps1
   ```

   Введите URL, service_role и пароль шифрования в скрытые поля. Не вводите ключи R2. На время копирования не загружайте и не удаляйте файлы школы. Секреты передаются дочерним процессам через временное окружение, затем прежнее окружение восстанавливается.
4. Дождитесь **`READY FOR MANUAL UPLOAD`**. В указанной папке внутри `artifacts/private-backups/manual` останутся `SlovaSofi-….restic.tar` и файл `.sha256`. Архив содержит зашифрованный restic-репозиторий с базой, файлами Storage, кодом текущего **коммита HEAD** и манифестом. Незакоммиченные правки не входят. Программа проверяет полное чтение зашифрованных блоков и извлечение из уже упакованного архива с SHA-256 исходных файлов, затем удаляет свои временные незашифрованные каталоги. Ошибка очистки также считается сбоем.
5. Откройте **Cloudflare → R2 → slovasofi-backups → Upload** и загрузите **только `.restic.tar` и `.sha256`**. Это ручные независимые копии, не отдельные объекты работающего автоматического restic-репозитория. Папки с SQL и скачанными файлами не загружайте. Публичный доступ не включайте.
6. После загрузки скачайте архив обратно, сравните `Get-FileHash -Algorithm SHA256` со значением в `.sha256` и локальным результатом. До этой проверки облачная загрузка не подтверждена. Храните также локальный архив и пароль отдельно от R2. При каждом новом ручном запуске создаётся отдельный архив; расписания и автоматического удаления нет.

Если запуск завершился ошибкой, он укажет конкретную рабочую папку. **Не загружайте её:** там могут оставаться незашифрованные школьные данные. После устранения причины удалите именно эту папку неудачного запуска. Удаление временных файлов не гарантирует физическое стирание данных с SSD — используйте доверенный компьютер с шифрованием диска.

Для извлечения скачанного архива распакуйте его командой `tar -xf` в **новую пустую папку**. Внутри будет `encrypted-repository`. Задайте локально `RESTIC_REPOSITORY` равным полному пути этой папки и `RESTIC_PASSWORD` равным сохранённому паролю, затем выполните `restic snapshots`, `restic check --read-data` и `restic restore SNAPSHOT_ID --target НОВАЯ_ПАПКА`. Проверьте извлечённые файлы командой `node tools/backups/verify.cjs НОВАЯ_ПАПКА`. Импорт базы сначала выполняйте в отдельный тестовый Supabase-проект по [полной инструкции](BACKUPS.md#полное-восстановление-школы), не поверх работающей школы.

Не входят настройки Dashboard Auth/SMTP/OAuth, секреты Edge Functions, ключи Vault и другие перечисленные в [полной инструкции](BACKUPS.md#что-будет-сохраняться) внешние параметры. Сохраните их отдельно в менеджере паролей.

## Автоматические копии — необязательный вариант

Программа и расписание подготовлены. **Настоящие облачные копии пока не включены:** нужно подключить новый аккаунт хранилища.

1. Откройте [Cloudflare](https://dash.cloudflare.com/), создайте аккаунт и закрытый R2 bucket `slovasofi-backups`, тип Standard. Публичный доступ не включайте. Получите ключ доступа только к этому bucket.
2. Создайте в [GitHub](https://github.com/new) **закрытый** репозиторий `SlovaSofi-backups`. Загрузите в него содержимое подготовленного комплекта, включая `.github`.
3. В GitHub Settings → Secrets and variables → Actions добавьте шесть секретов по таблице в [полной инструкции](BACKUPS.md#3-добавить-секреты-github). Пароли базы и шифрования храните также в менеджере паролей. В чат их отправлять не нужно.
4. В Actions запустите **SlovaSofi cloud backup**, включив `initialize` для первого запуска. Дождитесь успешного результата, затем повторите без `initialize` и извлеките пробную копию.
5. После проверки включите variables `BACKUPS_ENABLED=true` и `BACKUP_RETENTION_ENABLED=true`. Копии будут запускаться каждую ночь, храниться будут 30 дневных и 12 месячных версий.

В обычной работе ничего нажимать не потребуется. Для дополнительной копии перед большим изменением используйте Actions → Run workflow **без initialize**. Подпишитесь на уведомления о сбоях Actions и проверяйте свежесть последней успешной копии.

Не настраивайте удаление старых объектов средствами самого R2: restic хранит общие зашифрованные блоки для нескольких версий. Полная инструкция содержит проверку, ограничения расходов и порядок восстановления.

Если после повторной замены ключей остаётся `SignatureDoesNotMatch`, не создавайте новые токены вслепую. На доверенном Windows-компьютере из корня проекта запустите:

```powershell
powershell -NoProfile -File .\tools\backups\test-r2-access.ps1
```

Введите Access Key ID и Secret Access Key из одной сохранённой пары в скрытые поля терминала, не в чат. Проверка использует независимый от GitHub/AWS CLI клиент `curl`, запрашивает список с нулём результатов и ничего не изменяет в bucket. Ключи не записываются в файлы, переменные окружения или аргументы процесса. `SUCCESS` означает, что R2 принял эту пару; тогда проверяйте значения двух секретов GitHub. Повторный `SignatureDoesNotMatch` означает, что ошибка воспроизводится без GitHub; одной заменой workflow её не объяснить. Выводится только статус и код ошибки — их можно сообщить без ключей.

Если отдельно сохранилось исходное **API Token value**, запустите ту же команду с `-VerifyToken`. Третье скрытое поле запросит это значение. По [правилу Cloudflare](https://developers.cloudflare.com/r2/api/tokens/#get-s3-api-credentials-from-an-api-token) Secret Access Key равен SHA-256 от Token value. Проверка выполняется локально: `TOKEN_SECRET_MISMATCH` останавливает запуск до сетевого запроса; `TOKEN_SECRET_MATCH` подтверждает только соответствие секрета исходному токену, после чего выполняется обычная проверка R2. Она сама по себе не подтверждает Access Key ID, права или активность токена. Ни исходный токен, ни вычисленный ключ не выводятся.
