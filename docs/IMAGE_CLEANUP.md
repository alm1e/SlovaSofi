# Автоматическая очистка неиспользуемых фотографий

Подготовлены ежедневная проверка и удаление через Supabase Storage API. Локальный код не включает очистку в рабочем проекте: сначала примените миграции и опубликуйте функцию. До отдельного включения удаления все запуски работают как отчёт.

## Какие фото сохраняются

Проверяются только файлы `lesson-images` с именами, созданными сайтом: `UUID-пользователя/UUID-файла.png` (также JPG, JPEG, WebP, GIF). Не обрабатываются видео, аудио, записи учеников, сторонние ссылки и файлы с другими именами.

Файл сохраняется, если его идентификатор присутствует в уроке (включая домашние разделы, настройки, галереи и пометки), любой версии урока, ответах ученика, настройках кабинета, календаре, задании на дом, деталях журнала, защите нового черновика или списке изображений из исходников сайта. Архивирование класса само по себе не освобождает его фотографии. Фотографии из истории сохраняются даже после удаления текущего урока — иначе восстановление версии было бы неполным. Старые версии автоматически не удаляются.

В первый день файл лишь попадает в список кандидатов. Удаление возможно, когда файл старше **30 дней** и кандидат наблюдался ещё **14 дней**. Повторное использование снимает кандидатуру. За запуск обрабатывается не более **50** готовых кандидатов; обнаружение новых ограничено 1000 файлами. Перед каждым удалением повторно проверяются ссылки и идентичность объекта. Блокировки и запрет повторного использования удаляемого имени защищают от одновременного сохранения ссылки и удаления файла. При сообщении `image_unavailable` загрузите фото заново: оно получит новое имя.

Новые несохранённые уроки регистрируют ссылки черновика на сервере при автосохранении и повторном открытии. Защита не имеет срока: она снимается при сохранении нового урока или замене состава черновика. Незарегистрированные старые локальные черновики и файлы на компьютере сервер проверить не может. **До включения удаления откройте и сохраните нужные старые черновики во всех используемых браузерах.** Если регистрация защиты не удалась, сайт сообщает об ошибке сохранения черновика; сохраните полноценный урок. Перед включением проверьте также резервную копию Storage — SQL-копия не содержит байты файлов.

## Установка

1. Примените в SQL Editor [20261121_unused_lesson_images.sql](../supabase/migrations/20261121_unused_lesson_images.sql). По умолчанию `enabled=false`: удалений нет. Токен задания генерируется в закрытой таблице; копировать его или ключи в чат не нужно.
2. Обновите frontend и подготовьте список изображений из исходников:

   ```bash
   node tools/image-cleanup-source.cjs
   supabase functions deploy cleanup-images --no-verify-jwt
   ```

   `--no-verify-jwt` нужен для запуска Cron с отдельным секретным токеном. Сама функция проверяет его в базе **до** формирования плана; анонимный запрос ничего не удаляет. Серверный ключ используется только из окружения Edge Function. После добавления прямых Storage-ссылок в HTML/CSS/JS повторите генерацию и публикацию функции; тест проверяет актуальность списка. Ручные исключения можно добавить в `lesson_image_cleanup_protected` по UUID файла с причиной, отличной от `website-source`.
3. В Supabase **Database → Extensions** включите `pg_cron` и `pg_net` (либо установите Cron в разделе Integrations, если интерфейс предлагает это). Примените [20261122_schedule_lesson_image_cleanup.sql](../supabase/migrations/20261122_schedule_lesson_image_cleanup.sql). Расписание — **ежедневно 04:17 UTC**. Оно вызывает закрытую серверную функцию; проект URL уже соответствует конфигурации SlovaSofi.
4. Запустите предварительную проверку, не дожидаясь ночи:

   ```sql
   select public.run_scheduled_lesson_image_cleanup();
   ```

   Возвращённый номер означает, что HTTP-запрос поставлен в очередь, а не что очистка завершилась. Через несколько секунд проверьте отчёты:

   ```sql
   select started_at, finished_at, dry_run, result
   from public.lesson_image_cleanup_runs
   order by started_at desc limit 10;

   select name, first_seen_at, state
   from public.lesson_image_cleanup_candidates
   where state = 'pending'
   order by first_seen_at, name;
   ```

   До истечения первых 14 дней `eligible` будет нулём; список `pending` уже доступен для проверки. Не меняйте даты кандидатов для ускорения на рабочей базе. Если отчёта нет, проверьте Cron Job history, Edge Function logs и `select id,status_code,error_msg from net._http_response order by id desc limit 10;`.
5. После проверки кандидатов, регистрации черновиков и резервной копии включите удаление:

   ```sql
   update public.lesson_image_cleanup_settings set enabled=true where singleton;
   ```

   Следующие ночные запуски будут удалять готовые кандидаты. Старые отчёты предварительных запусков остаются доступны. Публично списки не видны; в API их может читать только администратор.

## Отключение и контроль

```sql
-- Вернуться к отчётам без удаления. Уже отправленный Storage-запрос отменить нельзя.
update public.lesson_image_cleanup_settings set enabled=false where singleton;

-- Полностью остановить ночные запуски.
select cron.unschedule('slovasofi-unused-lesson-images');
```

Успех означает `finished_at` заполнен, `result.failed=0`, а реально удалённое число — `result.deleted`. HTTP-статус с ошибкой или `storage_failed`/`unconfirmed` не считаются удалением. Неудачные объекты остаются заблокированными для новых ссылок до повторной проверки. После обрыва выполнения блокировка всего задания истекает через 10 минут, отдельные файлы повторно проверяются при следующем запуске. Имена удалённых объектов сохраняются как защитные записи; произвольные SQL-удаления из `storage.objects` не используются.

Новые таблицы входят в обычный полный SQL dump; расписание и настройку расширений после восстановления проекта нужно проверять отдельно. Это очистка Storage, она не удаляет аккаунты, уроки, ответы, историю или резервные копии.

Официальные инструкции: [удаление объектов](https://supabase.com/docs/guides/storage/management/delete-objects), [Cron](https://supabase.com/docs/guides/cron/quickstart).
