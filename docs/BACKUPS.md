# Постоянные резервные копии SlovaSofi

Если нужен **ручной вариант без R2 API и GitHub Actions**, используйте [ручное создание зашифрованного архива](BACKUPS_QUICK_START.md#ручная-копия-без-api-ключей-cloudflare). Он включает базу, файлы и код; готовый архив загружается через кнопку Upload в R2 Dashboard. Следующий раздел описывает отдельный автоматический вариант.

Подготовлен вариант **закрытый репозиторий GitHub Actions → шифрованное хранилище Cloudflare R2**. Он работает без включённого компьютера. Аккаунт R2 и секреты ещё нужно подключить; наличие этого файла само по себе не означает, что копии уже делаются.

## Что будет сохраняться

- База: схема, функции, RLS, роли и данные — уроки, классы, назначения, ответы, прогресс и аккаунты Auth.
- Файлы из всех обычных Storage buckets, включая закрытые записи учеников. Точный список берётся из того же SQL-дампа, а не из отдельного списка на текущий момент.
- Код сайта и Edge Functions из текущего коммита `alm1e/SlovaSofi`, миграции и инструкции.
- Манифест с датой, версией кода, количеством строк и SHA-256 каждого файла.

После каждой выгрузки программа извлекает именно новый снимок обратно из R2 во временный каталог и сверяет манифест и SHA-256 всех файлов. Только после этого запуск считается успешным и допускается очистка старых версий. Это проверяет извлечение файлов; импорт SQL в отдельную базу остаётся самостоятельной проверкой полного восстановления.

База и Storage — разные системы. Они не дают общей транзакции. Программа сверяет размер и доступный ETag файла с метаданными снимка; отсутствующий или изменившийся файл приводит к ошибке. На время планового тестового восстановления и перед крупными изменениями лучше прекратить загрузку и удаление файлов.

Не входят: настройки Auth/SMTP/OAuth в Dashboard, пароли внешних сервисов, пароли пользовательских ролей PostgreSQL, секреты Edge Functions, корневой ключ шифрования Supabase/Vault, несохранённые браузерные черновики и код Edge Functions, которого нет в репозитории. Эти параметры нужно один раз записать в менеджер паролей и обновлять при изменении. Векторные Storage buckets исключены: эта схема предназначена для обычных файлов школы. Парольные хеши аккаунтов Auth при этом входят в дамп данных.

## Разовая настройка

### 1. Создать хранилище

1. Войдите или зарегистрируйтесь в [Cloudflare](https://dash.cloudflare.com/).
2. Откройте R2 и создайте bucket `slovasofi-backups`, класс **Standard**, предпочтительно с размещением в ЕС, если этот выбор доступен аккаунту.
3. Оставьте bucket закрытым: не включайте публичный URL и пользовательский домен.
4. Создайте R2 API token с доступом **Object Read & Write только к этому bucket**. Сохраните Account ID, Access Key ID и Secret Access Key.
5. Не добавляйте правила автоматического удаления объектов по возрасту! restic повторно использует блоки между разными версиями; удаление старых объектов хранилищем повредит новые копии. Удалением старых версий занимается только restic.

У Standard R2 на момент подготовки есть бесплатные 10 ГБ·месяц хранения и лимиты бесплатных операций. Это квота, а не обещание бесплатности при любом объёме: [актуальный тариф](https://developers.cloudflare.com/r2/pricing/). Не активируйте платные возможности без необходимости; если мастер требует платёжные данные или согласие с условиями, этот шаг выполняет владелец аккаунта.

### 2. Создать закрытый репозиторий автоматизации

Публичный репозиторий сайта остаётся на своём месте. Для расписания создайте отдельный **Private** репозиторий `SlovaSofi-backups` в [GitHub](https://github.com/new). У публичных репозиториев расписание может отключаться после 60 дней без активности; поэтому шаблон запускается только в закрытом репозитории.

Из папки сайта выполните:

```powershell
node tools/backups/prepare.cjs
```

В `artifacts/private-backups/cloud-backup-setup` появятся только файлы программы и workflow — без паролей и школьных данных. Загрузите содержимое этой папки, включая `.github`, в корень нового закрытого репозитория. Не загружайте сам каталог `artifacts/private-backups`: в нём могут быть настоящие копии данных.

### 3. Добавить секреты GitHub

В **закрытом** репозитории откройте **Settings → Secrets and variables → Actions → Repository secrets**.

| Секрет | Откуда взять |
| --- | --- |
| `SUPABASE_DB_URL` | Supabase → Connect → **Session pooler**, порт 5432. В строке нужен существующий пароль базы. Спецсимволы пароля должны быть URL-encoded. Это не пароль входа на сайт. |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → API keys → legacy `service_role`, серверный ключ. Он нужен для скачивания закрытых файлов и не должен попадать в клиентский код. |
| `RESTIC_REPOSITORY` | `s3:https://ACCOUNT_ID.r2.cloudflarestorage.com/slovasofi-backups/slovasofi` — замените ACCOUNT_ID. |
| `RESTIC_PASSWORD` | Отдельный случайный пароль шифрования, минимум 32 символа. Сохраните ещё одну копию в менеджере паролей вне GitHub и R2. |
| `R2_ACCESS_KEY_ID` | Access Key ID созданного R2 token. |
| `R2_SECRET_ACCESS_KEY` | Secret Access Key созданного R2 token. |

При повторном открытии секрета в GitHub поле значения будет пустым: это поле для замены, сохранённый ключ не отображается. Это не означает, что ключ удалён. Cloudflare показывает Secret Access Key только после создания токена; сохраните его в менеджере паролей. В GitHub нужно вставлять Access Key ID и Secret Access Key из одного и того же токена, без кавычек и подписей полей.

Если прямой запрос к R2 возвращает `SignatureDoesNotMatch`, проверьте соответствие Secret Access Key выбранному токену. Не меняйте все шесть секретов из-за этой ошибки. Если исходная пара не сохранилась, создайте новый R2 token с Object Read & Write только для `slovasofi-backups` и замените два секрета `R2_ACCESS_KEY_ID` и `R2_SECRET_ACCESS_KEY` вместе. Новый токен и пароли вводит владелец аккаунта.

Для генерации пароля локально можно выполнить:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Не отправляйте пароли и ключи в чат, не записывайте их в workflow, документы или исходники. Не сбрасывайте действующий пароль базы только ради настройки копий: используйте сохранённый пароль; изменение может затронуть другие подключения.

### 4. Проверить первый запуск

1. Откройте **Actions → SlovaSofi cloud backup → Run workflow**.
2. Включите **initialize** только для первого создания пустого restic-репозитория.
3. Дождитесь зелёного результата. В Summary должны быть ID снимка, количество таблиц, число файлов Storage и время успешного завершения.
4. Повторите ручной запуск уже **без initialize**. Проверьте, что появилась вторая версия и сохранилась первая.
5. В Summary должна быть строка `Cloud file restore: verified by SHA-256`. Извлечение файлов уже проверено автоматически. Для проверки полного восстановления базы выполните импорт в отдельный тестовый проект по инструкции ниже.

Если соединение, SQL-дамп, скачивание файла или проверка restic завершатся ошибкой, запуск будет красным. Программа не считает частичную выгрузку успехом и не удаляет прежние версии. Незашифрованные SQL и файлы не публикуются как GitHub artifacts.

### 5. Включить постоянную работу

В **Settings → Secrets and variables → Actions → Variables** добавьте:

| Variable | Значение |
| --- | --- |
| `BACKUPS_ENABLED` | `true`: ежедневный запуск в 03:17 UTC, зимой в Братиславе 04:17, летом 05:17. |
| `BACKUP_RETENTION_ENABLED` | После проверки первого восстановления поставьте `true`: оставлять последние 30 дневных и 12 месячных версий, остальные удалять через restic. До включения старые версии не удаляются. |

30 дневных версий — это 30 дней, в которые были успешные копии, а не гарантия отсутствия пропусков. Политика действует только на снимки этого проекта и хоста SlovaSofi. Очистка запускается после новой успешной выгрузки и проверки. На первое число месяца назначена полная проверка сохранённых блоков; в остальные дни проверяется чередующаяся седьмая часть.

GitHub cron может задерживаться и не является сервисом с гарантированным временем запуска. Подпишитесь на уведомления о неудачных Actions в настройках GitHub; раз в неделю проверяйте, что последняя успешная копия не старше 36 часов. Отдельный независимый контроль отсутствия запусков можно подключить позже.

## Ограничения расходов

restic шифрует содержимое и имена файлов до отправки и повторно использует одинаковые данные. По умолчанию программа остановится, если:

- общий размер скачиваемых файлов Storage превышает **128 МиБ** за запуск;
- размер restic-репозитория достигает **8 ГиБ** или новая копия может превысить этот порог.

Первый предел ограничивает ежедневный исходящий трафик Supabase, второй оставляет запас до бесплатной квоты R2. Это не полноценные платёжные лимиты аккаунта: другие buckets, операции, минимальные блоки restic и сопутствующие сервисы тоже влияют на расходы. При росте школы лимиты можно изменить через `BACKUP_MAX_STORAGE_BYTES` и `BACKUP_MAX_REPOSITORY_BYTES`, предварительно проверив тарифы и период хранения. Не повышайте их автоматически при ошибке.

## Как извлечь и проверить копию

На доверенном компьютере установите [restic](https://restic.readthedocs.io/en/stable/020_installation.html), задайте `RESTIC_REPOSITORY`, `RESTIC_PASSWORD`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION=auto` безопасным способом. Для локальных запусков программы можно использовать игнорируемый Git файл `.env.backups` по образцу `tools/backups/backup.env.example`.

```powershell
restic snapshots --host SlovaSofi --tag project:vvrxhiextryjnzpxvals
restic check --read-data
restic restore SNAPSHOT_ID --target RESTORED_DIRECTORY
node tools/backups/verify.cjs RESTORED_DIRECTORY
```

Используйте новый пустой каталог. Замените SNAPSHOT_ID на ID подтверждённой успешной копии. Из-за относительного пути при backup каталог восстановления должен содержать `manifest.json`, `database`, `storage` и `source.tar.gz`. Если restic создал промежуточную папку, передайте `verify.cjs` папку непосредственно с `manifest.json`.

`verify.cjs` проверяет SHA-256 и размер каждого файла, состав SQL-дампа и соответствие всех файлов Storage снимку базы. Это проверка файлов, а не запуск восстановленной базы.

## Полное восстановление школы

1. Сохраните текущую базу отдельно, если она доступна. Зафиксируйте время выбранной копии и ожидаемую потерю изменений после этого времени.
2. Сначала восстановите на отдельном тестовом Supabase-проекте совместимой версии Postgres, а не поверх работающей школы.
3. Подготовьте необходимые расширения и примените официальный порядок [восстановления Supabase](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore): роли, схема, данные. Импорт запускается в транзакции с остановкой при ошибке и отключением триггеров на время импорта. Не переносите эти команды на рабочую базу без отдельной проверки.
4. Обычный SQL-дамп уже содержит метаданные Storage, но не физические файлы. Файлы `storage/*.bin` нужно загрузить в соответствующие `bucket` и `name` из манифеста через поддерживаемый Storage/S3 API. При совпадающих метаданных используйте проверенную процедуру восстановления с upsert; после загрузки сверьте владельцев и политики доступа. Не делайте прямые INSERT/DELETE в `storage.objects` для восстановления бинарных файлов.
5. Если использовались Vault или шифрованные колонки, восстановите исходный encryption root key по документации Supabase; SQL-дампа для них недостаточно.
6. Восстановите настройки Auth/OAuth/SMTP, секреты и Edge Functions из `source.tar.gz`, включите нужные Realtime publications и исправьте адреса проекта в тестовой копии сайта. Для нового проекта выдаются новые API keys; старые сессии могут потребовать повторного входа.
7. Проверьте вход преподавателя и ученика, классы, открытие урока, сохранённые ответы, картинку, аудио, закрытую запись и отправку нового ответа после обновления страницы.
8. Только после успешной проверки выбирайте способ переключения рабочего сайта.

Раз в месяц делайте такое пробное восстановление. Расходы на отдельный проект и реальные изменения рабочей базы требуют отдельного решения владельца.

## Что проверено при подготовке

Проверены текущий тариф Free, наличие таблиц и объёмы Storage агрегированными read-only запросами, без вывода содержимого уроков или персональных данных. 20 локальных тестов проверяют разбор SQL COPY, ссылки и имена файлов, хеши, ошибки загрузки и запрет очистки после ошибки. Официальный restic 0.19.1 с проверенной SHA-256 действительно создал зашифрованную копию искусственных данных, извлёк все файлы с совпадающими хешами и отказал при неверном пароле. В CI этот тест выполняется до доступа к рабочим секретам. 29 октября 2026 года проверено наличие всех шести секретов и выполнены два облачных запуска. Оба остановились до выгрузки базы: R2 вернул Access Denied. Проверка формата ключей и Account ID прошла. Дополнительный прямой запрос AWS CLI подтвердил совпадение Access Key ID с токеном в Dashboard и вернул SignatureDoesNotMatch. Требуется исправить Secret Access Key либо заменить пару ключей одного токена. Доступ к объектам пока не подтверждён. Расписание и очистка старых версий не включены. После исправления подключения требуется успешная выгрузка и проверка обратного извлечения.
